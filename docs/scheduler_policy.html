§ 3.4 — ARCHITECTURAL BACKDROP

Instance Disaggregation

The transformer layer is split at the attention/FFN boundary into two instances connected by an NVLink pipeline. This split is the prerequisite for everything in the scheduler policy that follows — KV cache permanence, fixed-shape handoff, and the Instance A internal joint GPU·PIM scheduling.

§ 6.2 · § 6.3 — STATIC RULES

Invariants & Dispatch DAG

The scheduler's policy reduces to a graph problem. Invariants (correctness + efficiency + resource) become edges in a per-μ-batch dependency DAG, and the dispatch decision collapses to picking a ready node.

Invariants (I1 — I5)

Whichever policy the scheduler adopts, these five rules cannot be violated. I1·I2 are correctness invariants (data dependency); I3 is an efficiency invariant (split O-proj is mathematically equivalent, but is strictly never split due to weight reuse · MFU · kernel launch penalties); I4·I5 are hardware resource constraints.

IDKindRule
I1 correctness prefill-attn(X) → dispatch only after QKV(X) completes (Q, K, V dependency)
I2 correctness decode-attn(X) → dispatch only after QKV(X) completes (PIM FSM start condition)
I3 efficiency O-proj(X) → dispatch only after both prefill-attn(X) ∧ decode-attn(X) complete. Although row-wise independence permits splitting, the penalties of W_O 2× streaming + MFU drop + 2× kernel launch keep it always a single GEMM. Aligned with the production mixed-batch standard pattern.
I4 resource At time t, the GPU resource runs only one GEMM / attention op (tensor core saturates; kernel concurrency ineffective).
I5 resource At time t, the PIM resource runs only one decode-attn op (SP-PIM occupies all 2048 channels). Not a head- or request-level constraint — within a single decode-attn op, multi-head · multi-request batching is free.

Dispatch DAG

DEFINITION Directed Acyclic Graph. Nodes are work units; an edge A → B denotes the precedence relation “B can be dispatched once A completes.” Acyclicity precludes deadlock and guarantees topological order. PULS encodes the §6.2 invariants as DAG edges, reducing the dispatch decision to a ready-node selection problem over a data structure.

Nodes. For each μ-batch X, four work nodes: QKV(X), prefill-attn(X), decode-attn(X), O-proj(X).

Edges. I1·I2·I3 become precedence edges directly:

EdgeSource invariant
QKV(X) → prefill-attn(X)I1
QKV(X) → decode-attn(X)I2
prefill-attn(X) → O-proj(X)I3
decode-attn(X) → O-proj(X)I3

§ 6.3 — RUNTIME MECHANISM

Scheduler Usage

How the scheduler actually runs at each kernel-completion event: maintain the DAG over a 2-active + transition-tail (capacity 3) window, refresh the ready set, and let two pick calls (one per resource) drive dispatch. The whole policy fits in nine lines.

Pseudo-code

The scheduler maintains a DAG over the in-flight μ-batch window {Mi-1, Mi, Mi+1}, and at every kernel-completion event dispatches ready work from the two queues (GPU·PIM).

on event(kernel K of μ-batch X completes):
    update DAG: mark node K(X) as done
    refresh ready set: all unexecuted nodes whose precedences are done

    GPU_next = pick(ready GPU jobs,
                    priority: O-proj > prefill-attn > QKV,
                    tie-break: oldest μ-batch first)
    PIM_next = pick(ready PIM jobs,
                    tie-break: oldest μ-batch first)

    if GPU idle: dispatch GPU_next
    if PIM idle: dispatch PIM_next

pick — definition

PRIORITY-QUEUE DEQUEUE A function with arguments (candidate set, priority rule, tie-break rule). Behavior: among candidates, narrow down to nodes belonging to the top-priority class of the priority rule, then pick a single node within that subset via the tie-break rule. Returns null if the candidate set is empty (in which case the resource sits idle).

GPU priority rationale — O-proj > prefill-attn > QKV

Why O-proj first. Delaying O-proj is a delay of the current μ-batch's completion and thus directly impacts the critical path. Once O-proj is ready (I3 satisfied), nothing else on the queue should jump ahead of it.

Why QKV last. QKV is the next μ-batch's enabling work, not the current one's critical path. It is prioritized only when the higher-priority classes are empty — that is, only when there is a risk of PIM going idle (no current-μ-batch attention or projection work left to do).

This ordering keeps the GPU lane continuously loaded: when O-proj is blocked (waiting on PIM for I3) and prefill-attn is also not ready (its μ-batch's QKV not yet done), the dequeue falls through to QKV of the next μ-batch — so the GPU stays busy and PIM decode-attn overlaps the compute-bound stages rather than serializing behind them.

Sync guarantee

Since I3 is auto-enforced as a DAG edge, there is no risk of missing synchronization. The DAG itself encodes the precondition; a node simply does not enter the ready set until its precedences are done.

Owing to PIM FSM determinism (§3.1), the PIM completion time is computed at the moment PIM is dispatched. The scheduler therefore knows in advance when O-proj will become ready, and the next GPU dispatch can be pre-scheduled to that exact moment.

§ 6.4 — THE OPERATING POINT

Admission: The Operating Point

Each μ-batch is composed to drive the three resources (PIM decode-attn · GPU-A projection+prefill-attn · FFN) to equal time. Composition is three separate concerns, each steered independently to a fixed target by local-greedy steering + an age-cap — not one cohort regulated by idle-fraction feedback.

Three separate concerns

  • Admission = pool refill only. request_queue → in-flight (PREFILL), gated solely by the aggregate KV budget. It does not look at the decode/prefill targets. A request with prompt_len = 0, or whose prefill is already done, transitions straight to DECODE.
  • Decode-set steering. From the in-flight DECODE pool, select a set hitting two targets at once — count 62 ∧ Σkv 6.15M — by local-greedy steering + age-cap. Pure selection (KV is reserved at pool entry).
  • Prefill steering. From the in-flight PREFILL pool, distribute 128 tokens (the fixed FFN-batch knob) so the PREFILL_ATTN depth-sum hits 12.8M, by the same per-token steering + age-cap. A member that receives 0 tokens stays in the pool.

These three concerns run every iteration. Per-iteration recomposition: after each forward pass the μ-batch is re-selected from the pool, disjoint from the other active μ-batch. The window holds 2 active μ-batches (capacity 3 = 2 active + 1 transition slack) — the staggering precondition for F2/F3 overlap. This is the real continuous-batching paradigm: a standing pool mixing decode / prefill / just-finished-prefill, recomposed every iteration — not a fixed cohort.

The count (62) is independent of KV length (FFN sees only token count); the KV sum (6.15M) is the sum of lengths (PIM sees only the sum). ctx 100K is a hardware constant (prefill cancels out of the triple balance) used only to derive the targets — never imposed on the workload.

Local-greedy steering + age-cap (the former algorithm)

The control target is the pair (count 62, Σkv 6.15M) — not a single average. Pure FIFO catches Σkv but misses the count on an off-average pool (spread 22–30%). So at each step the scheduler computes the length it next needs and admits the decoder closest to it; a request that has waited ≥ AGE_CAP is force-included (fairness). No global statistics, purely local:

one μ-batch (decode):                 # AGE_CAP = 5
  n=0, S=0
  while n < target_count(62) and S < target_kv(6.15M) and pool:
    if any request with wait ≥ AGE_CAP: admit the oldest        # fairness (forced)
    else: admit decoder closest to ideal=(target_kv−S)/(target_count−n)  # steering
  remaining waiters: wait += 1
  → converges to (62, 6.15M); n increases monotonically → ≤62 steps.
prefill: distribute 128 tokens to depth-sum 12.8M by the same steering + age-cap.
  • ★ Length-distribution-agnostic. On a heavily varied pool, short + long requests are combined to hit both targets — the average is never read. Heavy / mixed / bimodal all converge. Even an age-cap-forced off-size request is corrected by steering (a forced long request lowers ideal → the next picks several short ones).
  • Operating parameters = target_count + target_kv + AGE_CAP. The ±10% band [5.55M, 6.77M] is not a control value — it is a diagnostic idle-SLA label; steering hits the target so realized idle ≈ 0.
  • AGE_CAP trade-off (sweep). cap↑ → steering freedom↑ → spread↓ but latency↑; cap↓ → FIFO-like → fair/low-latency but spread↑. cap1: 3.1% · cap2: 1.2%, wait ≤3 · cap5: 0.7%, wait 5 · cap∞: 0.8% but starvation (wait 37) → AGE_CAP = 5 adopted (wait 5 ≈ 128 µs ≪ TBT, so latency-harmless; spread 0.7%).
SUPERSEDED Earlier drafts adjusted admission per iteration from measured GPU/PIM idle fractions + a hysteresis deadband. That feedback model is replaced by this pool model: the scheduler hits fixed targets via steering rather than reacting to measured idle (deadband σ was unmeasurable on a self-authored framework). The ±10% band survives only as a diagnostic idle-SLA label. See ARCHITECTURE.md §6.4.
§ 7 — CLUSTER ROUTING

Global Scheduler — Per-Node 100K Centering

The balanced operating point exists only when a node's in-flight pool is centered at mean ~100K — only then does the local steering (§4) hit (62 ∧ Σkv 6.15M). At server scale (hundreds–thousands of nodes) the global arrival mean drifts above 100K, so a server-level global scheduler routes requests to seat each node at that operating point.

Why it exists

Without centering, each node's pool tracks the global arrival mean and drifts high: a node then fits fewer decoders, so a batch falls below count 62 while Σkv rises above 6.15M — both control targets break together and idle blows up. The global scheduler keeps every node centered at 100K so the per-node steering can compose the operating point.

Core logic

  • Edge nodes + greedy cold-start (startup). Sort arrivals descending and shed the longest to dedicated edge nodes until the remaining mean ≤ 100K + E; then interleave-greedy pack the rest (each into the node whose mean lands closest to 100K). Long + short interleave so count · cap · mean-100K are satisfied at once.
  • Per-node steering + age-cap 5 (in batch). On each centered node, the §4 local-greedy steering composes (62, 6.15M); the age-cap (5) guarantees fairness — bounded wait, no starvation.
  • Greedy healing (operation). On each completion, refill the freed hole like-for-like (ideal = hole = toxic-fit): a long leaves → a long enters. This preserves the diverse centered pool — no eviction, no inter-node swap.
